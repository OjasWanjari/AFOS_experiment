## 3. Correct the save path

Inside `retrain()`, the save call corresponding to original line 246 must be:

```python
model.save(
    str(root / "models" / f"{name}_seed_{seed}.keras"),
    include_optimizer=True,
)
```

Inside `search()`, the best-search-model path should remain:

```python
model.save(
    str(root / "models" / f"best_search_seed_{seed}.keras"),
    include_optimizer=True,
)
```

**Do not use `best_search_seed_{seed}.keras` inside retraining.** All candidates with that seed would save to the same file and could overwrite the search model. Retraining files must remain distinct, such as `discovered_01_seed_0.keras`, `discovered_02_seed_0.keras`, and `relu_seed_0.keras`.

The `.keras` format stores the model and training state. Replacing this call with `model.export()` is not necessary for this workflow. [Official Keras saving documentation](https://keras.io/api/models/model_saving_apis/model_saving_and_loading/)

## 6. OOM mitigation and diagnosis

**The missing-extension save error and GPU out-of-memory errors are separate problems.** The final failure in this submission is the save error. Reproduction of OOM on another computer alone does not establish an XLA memory leak.

The model has only 306,234 parameters, but training also needs intermediate tensors, gradients, operation workspaces, and runtime resources. The original code uses `clear_session()` and `del model`; these calls alone do not demonstrate that memory remains bounded over a long run.

Proceed in this order:

1. Fix saving and run retraining in a fresh Python process, separate from the completed search.
2. In another terminal, run `nvidia-smi -l 5`. Observe VRAM use and other GPU processes at startup, between candidates, and near failure.
3. If OOM recurs, prepare a differently named recovery copy from the original saved run with `--disable-xla` and compare behavior. Do not overwrite an existing recovery directory.
4. If memory continues growing across trials without XLA, consider implementing one child process per function/seed trial, exiting after model saving and checkpoint updates.
5. If the first candidate fails in a fresh process, investigate its peak allocation and available VRAM. Process isolation alone may not solve a single-trial capacity problem.

`--disable-xla` sets `model.compile(..., jit_compile=False)` in the copy and records the change. It can affect speed and numerical results and does not guarantee OOM resolution. The helper does not implement per-trial child-process isolation. [Official Keras compile documentation](https://keras.io/api/models/model_training_apis/)

Changing batch size from 64 changes experiment conditions and is outside this recovery procedure. Do not turn OOM into a `nonfinite` score of zero and continue: failure to evaluate must be distinguished from numerical divergence. The helper does not rewrite the broad search exception handler, but the search is never executed under `--stage retrain`.
